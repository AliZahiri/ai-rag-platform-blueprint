# v0.4.0 — Operational Readiness and Recovery Evidence

Status: Released on 2026-11-03.

## Release intent

`v0.4.0` extends the offline RAG release-control baseline with operational
readiness checks, model-route workload contracts, evaluation release gates, and
an isolated vector-store restore drill. Default validation remains provider-free
and does not require paid API calls.

## Highlights

- Added deterministic retrieval-evaluation metric and decision-record gates,
  plus a release gate for evaluating retrieval quality against a reviewed
  baseline.
- Added LiteLLM fallback workload contracts so configured fallback routes can
  be checked against representative workloads before release.
- Added a bounded platform-readiness collector for Qdrant, Prometheus, Grafana,
  and optional LiteLLM probes. Strict mode can block on degraded required
  services, and reports avoid exposing response bodies or raw network errors.
- Added an isolated Qdrant restore drill that snapshots a source collection and
  verifies restoration against a separate target without modifying the active
  vector store.
- Added retrieval-source lifecycle checks for ownership coverage, change
  budgets, deprecation, and supersession; stack readiness now rejects stopped
  required services and missing or unhealthy health checks.
- Updated Qdrant Compose health checks to use commands supported by the pinned
  image.

## Compatibility and upgrade notes

- The release-check manifest remains at schema version `1`. The new checks are
  additive, and existing gate entry points remain available.
- No application-data migration is introduced. Review the new examples and
  opt into the additional gates in custom manifests as appropriate.
- The restore drill requires a separate, empty target Qdrant service. Do not
  point it at a shared or production instance; the documented cleanup command
  removes only the dedicated drill project's target volume.

## Known limitations

- Offline policy and evaluation gates validate supplied configuration and
  evidence; they do not establish that a production corpus, model provider, or
  retrieval result is trustworthy.
- The readiness collector checks bounded HTTP endpoints. A passing result does
  not establish end-to-end answer quality or prove that optional services not
  selected for probing are healthy.
- The restore drill validates a controlled snapshot/restore path against a
  separate target. It is not a substitute for a production recovery exercise,
  retention policy, or backup-isolation controls.
- Default CI uses deterministic fixtures and does not run live provider calls
  or a live Compose restore drill.

## Rollback

This release adds offline validation, readiness reporting, and an isolated
restore drill; it does not migrate application data. Operators can pin their
checkout to `v0.3.0` while investigating an adoption issue. Do not use the
restore drill's cleanup command against any project other than its dedicated
target, and do not bypass a failing release gate to complete a rollback.
