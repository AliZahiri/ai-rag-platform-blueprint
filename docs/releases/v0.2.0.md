# v0.2.0 — Offline RAG Release Controls

Status: approved for publication on 2026-09-16. This document is the source for
the GitHub Release notes.

## Release intent

`v0.2.0` turns the initial infrastructure blueprint into a testable offline
release-control baseline. It provides deterministic policy checks for the
configuration and evidence around a RAG platform without requiring live model,
vector-store, or paid provider calls in default CI.

## Highlights

- A single versioned manifest runs the core release gates and returns one JSON
  decision with stable exit-code semantics.
- LiteLLM routing, citation freshness, retention, vector backup coverage, and
  replica consistency are validated together before release.
- Quality and safety helpers cover retrieval, citations, evaluation, privacy,
  response safety, token and cost budgets, provider behavior, and index
  recovery evidence.
- The release runner accepts only allowlisted gate names, avoids shell
  execution, bounds arguments and runtime, and reports malformed inputs as
  execution errors rather than policy failures.
- CI remains provider-free and now executes the same unified manifest used by
  operators for release readiness.

See [`CHANGELOG.md`](https://github.com/AliZahiri/ai-rag-platform-blueprint/blob/v0.2.0/CHANGELOG.md)
for the categorized change list.

## Compatibility and upgrade notes

- Manifest schema version `1` remains current.
- Existing CLI entry points remain available; the unified runner coordinates
  them rather than replacing them.
- No persisted data or configuration migration is required.
- Teams adopting the runner should copy the example manifest, pin it in their
  own release configuration, replace sample evidence with reviewed evidence,
  and archive the aggregate JSON report with their release artifacts.

## Known limitations

- Most controls validate supplied evidence; they do not prove that the evidence
  collector or source system is trustworthy.
- The example manifest contains deterministic sample evidence and is intended
  to verify the release-control implementation, not authorize a production
  deployment.
- Live provider and vector-store probes are outside default CI and must remain
  explicit, credential-scoped operator actions.
- Container references in the blueprint must be reviewed and pinned before
  production use.
- The unified manifest covers the runner's five allowlisted core gates. Other
  policy helpers are exercised by the unit suite until they gain stable CLI and
  manifest contracts.
- Secret scanning and push protection are enabled. Dependabot security updates
  are currently disabled, and no code-scanning alert feed was available during
  the release review.

## Release validation

Run from a clean checkout of the candidate commit:

```bash
python3 -m unittest discover -s tests
python3 scripts/rag_release_check.py examples/release-checks.example.json
python3 -m json.tool examples/release-checks.example.json >/dev/null
python3 -m json.tool schemas/rag-release-check-manifest.v1.schema.json >/dev/null
git diff --check v0.1.0...HEAD
```

Expected results:

- all unit tests pass;
- the aggregate release report has `status: pass`;
- all five allowlisted gates pass with zero errors and zero policy failures;
- the manifest and schema parse as valid JSON;
- the release diff contains no whitespace errors.

## Rollback

This release changes validation and documentation only; it does not migrate
runtime data. If a downstream pipeline cannot adopt the unified runner, pin the
repository to `v0.1.0` and continue invoking the individual gate entry points
while the compatibility issue is investigated. Do not bypass a failing policy
gate to complete a rollback.
